# Reasoning Effort uses user-defined per-model levels, scoped to freeform providers only

The trigger was a self-hosted model (Qwen3.8-Flash-Next, served via llama.cpp/llama-server) that only supports three reasoning-effort levels (`low`, `medium`, `xhigh`, no `high`) and defaults to `xhigh`, the most expensive one. We considered giving Neira its own fixed vocabulary (e.g. a universal Off/Low/Medium/High scale) mapped down to whatever a given backend actually supports. We rejected that: a model that only has `low`/`medium`/`xhigh` has no real "high" to map to, and guessing a mapping (is Neira's "High" the backend's `xhigh` or something between `medium` and `xhigh` that doesn't exist?) produces exactly the kind of silent misconfiguration this feature exists to prevent. Instead, the level list is whatever the user types when configuring a model: the backend's own vocabulary, verbatim, with one of those levels marked as the default.

This is also why the feature is scoped to only the five providers with no standardized reasoning control: named custom OpenAI-compatible endpoints, LM Studio, MLX, Ollama, and OpenRouter. Curated cloud models (OpenAI, Anthropic, Google, xAI, Cerebras, Groq) already have native mechanisms, mostly token budgets rather than effort levels, and folding those into the same per-model-defined-levels model would have meant either forcing a token budget through a level-string abstraction it doesn't fit, or building a second, parallel mechanism inside the same feature. Both were bigger than the problem in front of us. Extending to cloud providers, if it happens, is a separate design pass with its own trade-offs, not a variant of this one.

The trade-off: because levels are freeform strings, Neira can't validate them against what a backend actually accepts. A typo in the levels list, or a shape mismatch (e.g. `chat-template-kwargs` selected for a server that wants a flat `reasoning_effort` field), fails at request time on the provider's side, not at configuration time. There are only three delivery shapes today (`flat`, `chat-template-kwargs` for llama.cpp-style servers, `openrouter` for OpenRouter's unified `reasoning.effort`), because those are the two concrete backends behind the feature's trigger case plus OpenRouter's well-documented convention; a fourth backend with its own shape needs a new `ReasoningShape` variant, not configuration. This is deliberately not a fully generic passthrough (no raw-JSON-path field), trading some flexibility for a UI simple enough to actually configure.

**Amendment:** the "fails at request time" trade-off above turned out to understate the actual failure mode for one real setup. The feature's trigger case (Qwen3.8-Flash-Next) is served through a LiteLLM proxy in front of llama.cpp, not llama.cpp directly. Verified live against that exact endpoint: the `flat` shape (`reasoning_effort` at the request's top level, LiteLLM's own recognized param) changes the response measurably, 254 completion tokens at `low` versus 497 at `xhigh` on an identical prompt. The `chat-template-kwargs` shape, sent through the same LiteLLM proxy, does not fail (it returns 200), but produces byte-identical output (478 completion tokens, 423-char `reasoning_content`) regardless of whether the level is `low` or `xhigh`, meaning LiteLLM silently drops the field rather than forwarding it, and the backend falls through to its own default. So a shape can look configured and misconfigured identically: no error, a normal-looking response, and the level simply never takes effect. This is worse than the request-time failure the original trade-off assumed, since there's no signal to notice by. We didn't add shape-detection or a "does this shape actually work" self-test (that needs a live round-trip against the user's own endpoint, which is a bigger feature than a documentation note), but `REASONING_SHAPES` now carries a `hint` (shown under the shape picker in Settings) telling the user to verify `chat-template-kwargs` actually changes behavior before trusting it, and to prefer `flat` when a proxy sits in front of the backend.
